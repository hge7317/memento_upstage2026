# 팀 규칙

## 브랜치 전략
- `main`은 배포 브랜치. 직접 커밋 금지.
- 기능: `feat/설명`
- 버그: `fix/설명`
- 문서/설정: `chore/설명`
- 실험: `spike/설명`
- PR은 1인 이상 리뷰 승인 후 병합.
- 병합은 squash merge 기본.
- 병합 후 브랜치 삭제.

## 커밋 컨벤션
- 타입: `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `ui`, `perf`
- 형식: `타입(범위): 요약`
- 예: `feat(quick-memo): 빠른 메모 입력 화면 추가`
- 예: `fix(interview): 타임라인에서 평가 문장 분리 누락 수정`
- 한 커밋은 한 가지 변경만 담는다.
- 커밋 메시지에 민감정보 금지.

## PR 규칙
- PR 템플릿 작성 필수.
- 본문에 변경 목적, 관련 PRD 절, 테스트 방법, 위험/비고 포함.
- 기능 변경은 QA 확인 항목 점검.
- 민감정보(키, 토큰, 실제 사용자 데이터) 포함 금지.

## 이슈 규칙
- 버그/기능 요청 템플릿 사용.
- 버그는 재현 단계, 기대 동작, 실제 동작 포함.
- 기능은 우선순위(P0/P1/P2)와 사용 시나리오 포함.
- 출시 일정은 Milestone으로 관리.

## 라벨
- 우선순위: `p0`, `p1`, `p2`
- 유형: `feat`, `bug`, `docs`, `ui`
- 필요시: `question`

## 코드 리뷰 체크리스트
- 변경 목적 명확성
- PRD 해당 기능 요구사항 충족
- 질문 1개 원칙/미언급 명사 금지/X 후보 재사용 금지/평가 분리/불확실 보존 규칙 위반 여부
- 세션·원문·결과 격리 및 삭제 후 재접근 불가 여부
- 오류·다운로드·모바일 관점 반영 여부
- 문서 반영 필요 여부

## 문서 규칙
- PRD 기준 문서: `docs/PRD_v0.2.md`
- UX 문구, 상태 모델, 질문 정책, 결과 구조 변경은 PRD와 동기화
- 기능 변경 시 관련 절 함께 수정
