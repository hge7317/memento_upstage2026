# Memory Replay 팀 규칙

## 1. 브랜치 전략
- `main`만 배포 브랜치로 사용한다.
- 기능 개발은 `feat/설명`, 버그 수정은 `fix/설명`, 문서/설정은 `chore/설명` 브랜치에서 진행한다.
- PR은 1개 이상의 승인을 받은 뒤 병합한다.
- 병합 방식은 squash merge를 기본으로 한다.
- 병합 후 브랜치는 삭제한다.

## 2. 커밋 컨벤션
- Conventional Commits 형식을 사용한다.
- 타입: `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `ui`, `perf`
- 예: `feat: 빠른 메모와 후보 추출 화면 추가`
- 예: `fix(interview): 타임라인에서 평가 문장 분리 누락 수정`
- `main`에는 직접 커밋하지 않는다.

## 3. PR 규칙
- PR 제목은 변경 범위를 알 수 있게 작성한다.
- PR 본문에 다음을 포함한다.
  - 변경 목적
  - 관련 PRD 항목
  - 테스트 방법 또는 QA 시나리오
  - 위험 요소/미해결 사항
- 기능 변경은 반드시 PR 템플릿에 따라 작성한다.
- 민감한 정보(키, 토큰, 실제 사용자 데이터)는 절대 포함하지 않는다.

## 4. 이슈 규칙
- 기능은 이슈 템플릿을 사용한다.
- 버그는 재현 단계와 기대 동작/실제 동작을 함께 남긴다.
- QA 항목은 QA 시나리오 이슈 또는 체크리스트로 추적한다.
- Milestone을 사용해 출시 일정(9월 16일)에 맞춰 관리한다.

## 5. 코드 리뷰 체크리스트
- 변경 목적이 명확한가
- 규칙 위반이 없는가(질문 1개, 미언급 명사, 평가 혼입, X 후보 재사용 등)
- 사용자 입력/세션/삭제 흐름이 안전한가
- 모바일·오류 처리·다운로드 결과가 고려됐는가
- 문서에 반영이 필요한 변경이 있는가

## 6. 문서 규칙
- PRD는 `docs/PRD_v0.2.md`를 기준으로 한다.
- UX 문구와 화면 문구는 기능 브랜치에서 함께 수정한다.
- 상태 모델, 질문 정책, 결과 구조 변경은 PRD 및 구현 문서와 일치시킨다.

## 7. 개발 우선순위
- P0: 스플래시, 상황 탭, 빠른 메모, 후보 추출, O/X 검증, 면접 Step 1·Step 2, 면접 Markdown 결과
- P1: 분실물 찾기, 미팅 복기, PDF 결과, 모바일 최적화, 오류 복구·삭제·품질 로그
- P2: 음성 입력, D+1 추가 회상, 발표·심사 탭, 상황 탭 원격 설정
