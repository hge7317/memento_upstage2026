# GitHub 팀 규칙

## 1. 브랜치 전략
- `main`은 배포 브랜치다. 직접 커밋하지 않는다.
- 기능: `feat/설명`, 버그: `fix/설명`, 문서/설정: `chore/설명`, 문서 전용: `docs/설명`
- PR은 1인 이상 리뷰 승인 후 병합한다.
- 병합은 squash merge를 기본으로 한다.
- 병합 후 브랜치는 삭제한다.

## 2. 커밋 컨벤션
- Conventional Commits를 사용한다.
- 형식: `타입(범위): 요약`
- 타입: `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `ui`, `perf`
- 예시:
  - `feat: 빠른 메모와 후보 추출 화면 추가`
  - `fix(interview): 타임라인에서 평가 문장 분리 누락 수정`
- 한 커밋은 한 가지 변경만 담는다.
- 커밋 메시지에 민감정보를 적지 않는다.

## 3. PR 규칙
- PR은 템플릿을 작성한다.
- 본문에 다음 내용을 포함한다.
  - 변경 목적
  - 관련 PRD 절
  - 테스트 방법
  - 위험/비고
- 기능 변경은 PR 템플릿의 QA 확인 항목을 함께 점검한다.
- 민감정보(키, 토큰, 실제 사용자 데이터)는 절대 포함하지 않는다.

## 4. 이슈 규칙
- 버그와 기능 요청은 템플릿을 사용한다.
- 버그는 재현 단계, 기대 동작, 실제 동작을 적는다.
- 기능은 우선순위(P0/P1/P2)를 함께 표시한다.
- 출시 일정은 Milestone으로 관리한다.

## 5. 라벨
- 우선순위: `p0`, `p1`, `p2`
- 작업 유형: `feat`, `bug`, `docs`, `ui`
- 필요시 `question` 라벨을 사용한다.

## 6. 코드 리뷰 체크리스트
- 변경 목적이 명확한가
- PRD 해당 기능 요구사항을 만족하는가
- 질문 1개 원칙, 미언급 명사 금지, X 후보 재사용 금지, 평가 분리, 불확실 보존 규칙을 위반하지 않는가
- 세션·원문·결과 격리와 삭제 후 재접근 불가가 지켜지는가
- 오류·다운로드·모바일 관점이 반영됐는가
- 문서에 반영이 필요한가

## 7. 문서 규칙
- PRD 기준 문서는 `docs/PRD_v0.2.md`다.
- UX 문구, 상태 모델, 질문 정책, 결과 구조 변경은 PRD와 맞춘다.
- 기능 변경 시 관련 절을 함께 수정한다.
