# 구현 프롬프트 — Memory Replay 화면 시안 v5 기반 화면 구현

**목표**: 아래 시안 PDF의 화면 시안을 코드화한다. 시안에 묘사된 화면·레이아웃·구성요소를 재현하는 것이 목표이며, 시안에 없는 기능 확장·Backend 연동·상태관리 구조 변경은 이 프롬프트의 범위 바깥이다.

**입력 스펙**: `/Users/minseoklee/.hermes/attachments/메모리_화면시안_v5.pdf`

**기존 코드베이스**: 이 프롬프트를 실행하는 에이전트는 작업 시작 전 현재 저장소의 frontend/ 트리를 읽어서 기존 컴포넌트·스타일·라우팅 구조를 파악한 뒤 Stage B를 진행한다. 기존 코드가 없으면 "기존 코드 없음"으로 기록하고 Stage B에서 신규 컴포넌트 목록을 작성한다.

**처리 완료 목록 (이 프롬프트 실행 전)**:
```
처리 완료: (이 프롬프트 실행 전 완료된 단계가 있으면 여기 기재, 없으면 빈 목록)
```

**범위 바깥 (이 프롬프트에서 만지지 않는다)**:
- Backend API 연동, API 호출 코드 추가
- 상태 관리 구조 변경 (새로 도입해야 하는 경우 최소한으로만, 시안에 필요한 범위로 한정)
- 시안에 묘사되지 않은 화면·기능 추가
- 퍼포먼스 최적화·검사 코드·배포 설정
- 시안 외 디자이너 판단 개입

## Stage A: 코드 검토 (audit)

**작업**:
1. frontend/ 트리의 현재 구조를 읽는다. 주요 진입점, 라우팅, 기존 컴포넌트 목록, CSS/스타일 방식, 사용 중인 라이브러리를 확인한다.
2. 시안 PDF(`/Users/minseoklee/.hermes/attachments/메모리_화면시안_v5.pdf`)를 읽는다. 시안에 묘사된 화면 수, 각 화면의 구성요소, 레이아웃 특징, 반응형 조건을 추출한다.
3. 기존 코드와 시안을 대조해 다음 테이블을 작성한다:

| 시안 화면 | 기존 컴포넌트 대응 | 신규 필요 | 기존 재사용 가능 요소 | 시안-코드 간 불일치 |
|-----------|-------------------|-----------|----------------------|---------------------|
| (화면명)  | (대응 컴포넌트/없음) | (Y/N)   | (어떤 요소)          | (무엇이 다른가)     |

4. 시안에 텍스트 레이블·문구·아이콘·공통 UI 요소가 있으면 목록화한다.

**완료 기준**:
- [ ] 시안 PDF를 읽었고, 시안에 묘사된 화면 개수와 각 화면의 주요 구성요소를 식별할 수 있다
- [ ] 기존 frontend/ 구조를 읽었고, 주요 진입점·라우팅·컴포넌트·스타일 방식을 파악했다
- [ ] 위 대조 테이블을 작성했다
- [ ] 시안에서 텍스트 레이블·공통 UI 요소 목록을 추출했다

## Stage B: 컴포넌트 인벤토리 작성

**작업**:
1. Stage A 대조표를 바탕으로, 시안을 구현하는 데 필요한 컴포넌트 목록을 작성한다. 기존 컴포넌트 재사용과 신규 생성을 구분한다.
2. 각 컴포넌트에 대해 다음을 명시한다:
   - 이름 (기존이면 기존 이름, 신규면 시안 기준 작명)
   - 소속 화면
   - 책임 (무엇을 표시/처리하는가)
   - props 인터페이스 (상위에서 받을 데이터·콜백, 시안에서 추론 가능한 범위로 한정)
   - 재사용 여부 (기존 재사용 / 신규 / 기존 일부 수정)

**작성 형식 예**:
```
- 컴포넌트: (이름)
  - 화면: (어느 화면)
  - 책임: (한 줄)
  - props: (입출력, 확정 가능한 범위만)
  - 분류: 기존 재사용 / 신규 / 기존 수정
```

**완료 기준**:
- [ ] 시안의 모든 화면이 하나 이상의 컴포넌트에 대응된다
- [ ] 각 컴포넌트에 책임·props·분류가 명시된다
- [ ] 기존 코드 중 재사용 가능한 요소와 신규 생성 요소가 구분된다

---

## Stage C: 추출/매핑 테이블

**작업**:
1. 시안 PDF에서 추출한 디자인 요소(레이아웃, 컴포넌트, 텍스트, 공통 스타일)를 아래 컬럼으로 테이블화한다:
   - 시안 요소 ID (예: S-01, S-02 — 시안 내 등장 순서 또는 화면 기준)
   - 요소 유형 (레이아웃 / 컴포넌트 / 텍스트 / 아이콘 / 공통 스타일)
   - 시안 묘사 (무엇이 어떻게 표시되는가, 시안에서 읽을 수 있는 범위로 서술)
   - 매핑 대상 (기존 컴포넌트명 / 신규 컴포넌트명 / 스타일 규칙)
   - 구현 노트 (주의점, 시안에서 ambiguous한 부분, 판단 필요 사항)
2. 시안에서 여러 화면에 공통으로 등장하는 요소(헤더, 버튼 스타일, 카드 스타일, 타이포그래피 규칙 등)는 "공통"으로 표시하고 별도로 모은다.

**완료 기준**:
- [ ] 시안의 시각적 요소가 빠짐없이 테이블에 매핑된다 (시안 페이지/화면 단위 검수)
- [ ] 공통 요소가 별도로 식별된다
- [ ] ambiguous한 부분은 "판단 필요"로 표시된다 (임의 결정하지 않는다)

---

## Stage D: 구현 순서 결정

**작업**:
1. Stage C의 테이블을 바탕으로 구현 순서를 정한다. 판단 기준:
   - 공통 요소 → 개별 화면 순서 (공통을 먼저 해두면 개별 화면이 소비할 수 있다)
   - 시안의 화면 흐름상 앞에 오는 화면부터 (사용자가 처음 보는 화면 우선)
   - 의존 관계: A를 표시해야 B가 의미가 있으면 A 먼저
2. 순서 목록을 단계별 checkpoints와 함께 작성한다. 각 단계는 "무엇을 끝낸다"로 기술한다.

**작성 형식 예**:
```
1. (공통 요소) — (무엇을 끝내는가) — 완료 기준: (체크 가능)
2. (화면명) — (무엇을 끝내는가) — 완료 기준: (체크 가능)
```

**완료 기준**:
- [ ] 구현 순서 목록이 있다
- [ ] 각 단계에 체크 가능 완료 기준이 붙는다
- [ ] 공통 요소 우선 원칙이 반영된다

---

## Stage E: 구현

**작업**:
1. Stage D 순서대로 구현한다. 각 단계 종료 시 해당 단계의 완료 기준을 확인한다.
2. 시안에서 추출한 텍스트·레이아웃·구성요소·공통 스타일을 그대로 반영한다. 시안에 없는 해석·추가를 넣지 않는다.
3. 스타일이 시안과 다르면 시안을 우선한다. 기존 스타일과 충돌하면 시안 기준으로 작성하고, 충돌 지점을 구현 노트에 남긴다.
4. 시안에서 ambiguous한 부분은 임의로 결정하지 말고, Stage C에서 "판단 필요"로 표시한 항목을 모아 최소한의 확인 질문 형태로 정리한 뒤 진행한다. (질문이 불가능하면 가장 보수적인 기본값 — 시안에서 가장 단순하게 읽히는 쪽 — 을 선택하고 그 선택을 기록에 남긴다.)

**완료 기준 (단계별로 확인)**:
- [ ] 해당 단계의 완료 기준을 충족한다
- [ ] 시안에 묘사된 요소가 누락 없이 반영된다
- [ ] 시안에 없는 요소가 추가되지 않는다

---

## Stage F: 대조 검증

**작업**:
1. 구현 결과(렌더링 출력 또는 코드)를 시안 PDF와 화면 단위로 대조한다.
2. 각 시안 화면별로 아래 항목을 확인한다:
   - 구성요소 존재 여부 (시안에 있는 요소가 코드에 있는가)
   - 레이아웃 방향 (시안의 배치·비율·정렬과 합치하는가)
   - 텍스트 내용 (시안 레이블·문구와 일치하는가)
   - 공통 요소 일관성 (공통으로 쓰인 요소가 화면 간 동일하게 처리됐는가)
   - 시안에 명시된 반응형 조건 충족 여부 (시안에 반응형 묘사가 있으면 확인)
3. 불일치 사항을 아래 테이블로 기록한다:
   - 시안 요소 ID
   - 불일치 내용
   - 원인 (시안 모호 / 구현 누락 / 스타일 충돌 / 판단 차이)
   - 조치 (수정 / 유지 판단 / 추후 확인)

**완료 기준**:
- [ ] 시안의 모든 화면을 코드 대조했다
- [ ] 불일치 테이블이 작성됐다
- [ ] "시안 모호"로 인한 불일치는 임의 수정하지 않고 기록만 남긴다

## 가드레일

- **처리 완료 목록의 항목은 재방문하지 않는다.** 이미 끝난 Stage는 다시 하지 않는다. 재방문이 필요하면 범위 변경·오류 정정 등 이유를 명시한다.
- **완료 기준은 체크 가능해야 한다.** "비슷하게 만든다" 같은 모호한 바운드는 사용하지 않는다. "시안 S-01의 헤더가 존재한다", "시안 레이블 텍스트가 일치한다"처럼 관찰 가능한 조건으로 쓴다.
- **부정 대신 긍정으로 기술한다.** "시안에 없는 기능은 넣지 않는다"가 아니라 "시안에만 있는 요소를 구현한다"로 범위를 정한다.
- **같은 파일을 여러 Stage에서 중복 수정하지 않는다.** Stage E에서 실제로 수정할 파일만 Stage E에서 다룬다.
- **시안 외 판단 개입을 하지 않는다.** 시안이 모호하면 임의 결정하지 않고 "판단 필요"로 표시하고, 필요시 질문 형태로 분리한다.
